## Deterministic and synthetic validation

The final full suite ran 185 tests: 184 passed and one directory-symlink test was skipped because this Windows account cannot create directory symbolic links. Redirected-output rejection remains covered by supported filesystem tests and prior Windows junction evidence. The final package-focused run had 12 tests with the same single capability skip.

Coverage includes canonical DOI/arXiv/URL identities, exact file hashing, collision refusal, keyword reconciliation, v1-to-v2 SQLite backup/migration, library locks, complete paginated Base reads, field-ID mapping, verified creates/updates, fill-only collection, read-only intersection filters, explicit updates, strict bounded JSON, one-document stdout, reproducible packages and dependency allowlisting.

Remote mutations are tested through a real shell-free subprocess boundary using a synthetic CLI provider. The packaged launchers run from unrelated Unicode directories. Synthetic provider state proves that list and preview make zero writes, collection creates an unread record once, fill-only collection preserves curated fields, explicit update writes only requested field IDs, and same-value repeats are no-ops. Fault cases cover ignored fields, malformed exports, timeouts, uncertain create results, account/schema drift and verification failures. These tests validate orchestration and safety behavior; they do not constitute a real Lark mutation test.

The `add` and `library` bodies are identical across host packages and remain below 500 English words each. A fresh-agent forward evaluation of the packaged `library` skill passed its three observable tests and found no critical or important issue. Its behavior run exercised reading-status update; priority/keyword updates and error branches are covered by the service/CLI tests and explicit skill rules.

Codex quick skill validation passed for generated skills, the Codex plugin validator passed, and `claude plugin validate --strict --json` returned success without errors or warnings. The persistent Codex installation contained all four expected skills; their files matched the generated package and its installed runtime hash matched the build metadata. Public source, docs and generated artifacts are scanned for private paths, identifiers, caches, fixtures, raw provider output and unimplemented workflow claims.

## Existing-library read-only acceptance

The existing personal binding was checked with its saved user credentials. `doctor --verify` completed ordinary server verification/token refresh without starting login, logout or an authorization reset, and confirmed the bound Wiki parent, Base table, mapped fields, statuses and template. The exact personal record count is retained only in ignored private evidence; the complete count was obtained rather than inferred from a truncated page.

All 12 saved field-ID mappings matched the live schema. The live controlled vocabulary contained 45 distinct ASCII English labels, each within the three-word limit. An add preview built from an existing canonical identity reused the same record and returned `noop`; it did not create a title-based match. A same-value reading-status update preview also returned `noop` with an empty change set. Both reported `remote_mutations: false`.

The acceptance invoked only diagnosis, list, add preview and update preview. It never used `--apply`. Hashes and directory entries for the private binding, SQLite state and the rest of the Paper2Lark home were identical before and after. Raw resource IDs, record content, URLs, account data and exact personal record count remain outside this report.

## Support boundary

Windows with the exact versions above is the only environment exercised here. The runtime requires Python 3.11 or newer by contract, but macOS and Linux host execution remain unverified. Claude and Codex manifests, packaged launchers and synthetic workflows passed, as did the persistent Codex installation/update. A fresh interactive Claude `--plugin-dir` M2 host session remains a separate host-integration gate.

M2 manages an existing paper index only. M3 will add paper-source/model/template handoff; M4 will add verified Wiki-note publication and recovery; M5 will add new-library provisioning and customization. M2 does not read papers, summarize them, create or edit notes, provision Wiki/Base resources, or act as a general research knowledge agent.
