# M5 Provisioning and Customization Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans task-by-task. Review the complete diff before integration.

**Goal:** Create a configurable English/Chinese Wiki paper library, safely extend existing indexes, and retain recoverable setup progress.

**Architecture:** A small setup service owns immutable plans and an atomic private operation journal, separate from reading runs. A typed provisioning adapter uses allowlisted lark-cli commands. Existing bindings and template protection remain authoritative; migration is additive only.

**Tech Stack:** Python 3.11+ standard library, installed lark-cli, existing shared zipapp build.

**Spec:** ../specs/2026-09-13-paper2lark-design.md, R02/R09/R13/R16, M5, T08/T20/T31.

## Global Constraints

- No third-party runtime dependency; each generated plugin remains at most 262144 bytes.
- English instructions; `en` and `zh-CN` library assets; English keywords, three words/eight labels maximum.
- No production writes during development; no login/logout, destructive rollback, field conversion, or template overwrite.
- Both hosts use the same runtime and private home. Local setup artifacts survive updates.
- Preserve renamed fields by ID and retain user fields, options, views, records and template sections.

## Decisions

`setup plan --input FILE` captures either `create` or `migrate` intent and returns an immutable private plan path/ID. `setup apply --plan FILE` applies that exact saved plan; `setup show --id ID` reports recovery state. Plans freeze the profile/account, prior binding, language/assets and desired mappings. Resource environment overrides are rejected to avoid mixing targets.

Creation builds a new Wiki space, a root Docx node, an index bitable node, one explicitly defined 12-column table, a notes container and a template document. Creating the bitable directly in Wiki avoids an asynchronous Drive move. No default field/table is deleted. Only the final fully inspected resources become the binding.

Migration uses the bound physical table and explicit field/status maps, adds only missing logical fields, then verifies and atomically replaces the local binding. Existing compatible mappings survive display-name changes. Incompatible fields require explicit remapping; existing templates are inspected but never edited.

Before every remote write, persist intent. Completed operations are reused. A lost response is reconciled against read-back evidence where unambiguous; otherwise report an uncertain stage and require an explicit verified resource reference via `setup apply --adopt FILE`. Never repeat an uncertain create automatically. Failed setup retains all created resources, IDs and files. A profile lock serializes setup and a compare-and-save binding guard detects other local changes.
